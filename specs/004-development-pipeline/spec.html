PointApp Builder Development Pipeline

Objective

Adopt PointSite Builder's current Project-backed development process for PointCommunity/pointapp-builder while preserving PointApp Builder's distinct content-release, security, and native-application boundaries. Success means a private organization Project, one-active-Issue governance, repository-owned cross-agent skills, deterministic audits, complete CI/security gates, and exact-revision direct deployment of the Builder application to https://appbuilder.pointatx.org.

Confirmed assumptions and alignment decisions

  • The Project owner is PointCommunity; the private Project is PointApp Builder, number 5.
  • PointSite Builder Project number 1 is the structural source for fields, views, workflows, labels, skills, adapters, and audit mechanics.
  • The separate PointCommunity Project PointApp, number 3, governs native-app work and is not reused or modified.
  • Both Builder applications deploy directly to one production environment after exact-head review and exact-main CI; PointApp Builder has no application Staging or Canary.
  • PointApp Staging and Production are signed immutable content channels inside the Builder, not Builder deployment environments.
  • PR #7 on codex/003-complete-builder, PRs #8 and #9 on codex/oauth-live-fix, and pipeline-adoption PR #10 on codex/development-pipeline-bootstrap, plus PR #11 on codex/oauth-error-categories, predate this Issue pipeline. Those exact PR/branch pairs are its only bootstrap exceptions. No later product work may bypass a governed Issue.
  • This bootstrap changes repository governance and GitHub metadata only; it does not deploy the Builder, publish content, or touch PointCommunity/pointapp.

GitHub Project contract

Views Backlog and Kanban board views grouped by Status
Built-in workflows Keep item added → Backlog, linked pull request → In Progress, item closed → Done, Done → close Issue, and sub-issue addition enabled. Keep pull request merged → Done disabled because merge alone is not completion.
Repository Link only PointCommunity/pointapp-builder.

Every open Builder Issue belongs to the Project with populated Status, Priority, Impact, and Effort. Backlog Issues are open and unassigned. Active Issues are assigned only to brimdor. The copied Canary description for In Review is replaced with exact PR candidate language appropriate to direct Builder production.

Issue and label model

Each governed Issue has exactly one type:* label and one or more applicable area:* labels. The controlled taxonomy covers bug, feature, maintenance, security, authoring, data, deployment, documentation, identity, media, publishing, UI, and workflow. Existing generic and Dependabot labels remain available for compatibility.

State flow

  1. An explicitly approved HTML Issue draft is created open, unassigned, fully classified, added to the Project, and set to Backlog.
  2. PM selection moves the Issue to In Progress and assigns only brimdor.
  3. Implementation starts from current origin/main on issue/<number>-<slug>, with specification and tests before behavior.
  4. A PR containing Refs #<number> receives full agent QA, local browser verification, and exact-head GitHub Quality before the Issue moves to In Review.
  5. Unless the PM requested an earlier stop, the verified PR is squash-merged and its merge tree must equal the reviewed tree.
  6. The exact clean origin/main commit must pass GitHub Quality before direct Builder production deployment.
  7. Only verified live Builder production permits Project Done, Issue closure, and unassignment.
  8. A failed release restores the recorded Cloudflare version and keeps the Issue active for a reviewable fix.

Commands

  • npm run skills:check validates pipeline logic, skill registries, adapters, policy, and helpers.
  • npm run pipeline:health performs a read-only live Git, Issue, Project, PR, label, workflow, and CI audit.
  • npm run check runs skills, formatting, generated types, TypeScript, lint, contracts, migrations, coverage, dependency/source security, build, and bundle security.
  • npm run test:performance and npm run test:e2e remain separate full release gates.
  • npm run deploy verifies Cloudflare identity and production secrets before building and deploying exact clean origin/main.
  • npm run verify:live checks production health, security headers, HTTPS redirect, anonymous isolation, login initiation, derived assets, signed Production content, and ETag revalidation.

Testing strategy

  • Use Node tests for positive and negative pipeline snapshots and pure live-verification contracts.
  • Validate every canonical skill and regular-file adapter, including exact registry membership.
  • Run formatting, generated types, TypeScript, lint, contracts, migration tests, coverage, dependency/source/bundle security, build, performance, and Chromium/Firefox/WebKit browser suites.
  • Run the live read-only pipeline audit against Project #5 after GitHub setup.
  • Do not deploy production for this governance bootstrap; production verification remains a future Issue-closure gate.

Boundaries

  • Always: preserve user-owned work, read back GitHub mutations, verify exact candidate identity, keep migrations rollback-compatible, and keep application deployment separate from content publication.
  • Ask first: destructive schema/data recovery, adding another repository to Project #5, introducing a second Builder environment, or changing the native app.
  • Never: expose secrets, weaken authentication, close an Issue on merge alone, publish or promote content as part of application deployment, or touch PointCommunity/pointapp without authorization.

Platform limitation

GitHub currently rejects branch protection and repository rulesets for this private repository at the organization plan level. Repository skills and audits therefore enforce the PR, exact-tree, and Quality contract and report the limitation without claiming those unavailable controls are active.
