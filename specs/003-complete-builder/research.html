Phase 0 · Research · 7 September 2026

Decisions before implementation.

The Builder is a private control plane; the PointApp content feed is a public, signed, read-only data plane. The design deliberately separates those trust boundaries.

Platform and delivery

Worker-first API routing

Decision
Run the Worker first for authentication, API, media, health, and content-channel routes while leaving fingerprinted static assets on the asset path.
Rationale
Cloudflare Workers Static Assets supports selective Worker-first routes and SPA fallback without exposing protected records through the public bundle.
Alternatives
GitHub Pages cannot safely host authenticated mutations for a private repository on the organization’s current plan; a separate API would add deployment coupling.

D1 transactional persistence

Decision
Use prepared statements and D1 batches for membership transitions, immutable saves, publication pointers, and audit records.
Rationale
D1 batches execute sequentially as a transaction and roll back the sequence on failure. Database constraints remain the source of truth.
Alternatives
Browser storage is not authoritative or shareable. Repository commits would make routine app-content publication slow and would require broader GitHub permissions.

Rate limiting

Decision
Use Cloudflare Rate Limiting bindings keyed by authenticated actor and operation, with narrow IP-based limits only for unauthenticated login/callback abuse.
Rationale
The binding is fast, but is local and eventually consistent; it is suitable for abuse resistance, never authorization or exact quotas.
Alternatives
In-isolate maps are unreliable across isolates. A D1-only counter would add contention to every mutation.

Identity and authority

Existing GitHub App

Decision
Reuse the organization-owned pointsite-builder GitHub App for user OAuth with a new exact callback URL and configure its installation for all organization repositories without adding permissions.
Rationale
One organization integration matches the user’s request. OAuth identity and installation repository access remain distinct. PointApp content itself stays in D1.
Alternatives
A second app fragments management; Cloudflare Access would not provide the requested first-login/pending-user workflow.

Owner bootstrap

Decision
Only immutable GitHub user ID 1202831 may atomically become Owner in an empty installation. Every other new identity is inserted as Pending Editor.
Rationale
This prevents an arbitrary internet visitor from winning a first-request race and avoids trusting a mutable login name.
Alternatives
“First visitor wins” is unsafe. Environment-only role lists do not support ongoing Owner administration.

Registration boundary

Decision
Assume any valid GitHub identity may create a Pending Editor request; pending users receive no protected data. This remains a reviewable assumption until the Owner confirms whether registration should instead require organization membership.
Rationale
It supports volunteers while retaining explicit Owner approval and avoids increasing GitHub App permissions.
Alternatives
Organization-members-only signup reduces request noise but requires an organization-membership check and may exclude legitimate non-member contributors.

Content integrity

Canonical manifests

Decision
Recursively sort JSON object keys, serialize deterministically, hash with SHA-256, and sign the digest-bearing release envelope with Ed25519.
Rationale
Cloudflare Web Crypto supports Ed25519. Identical manifest bytes produce an identical digest independent of channel.
Alternatives
Signing ordinary JSON.stringify output risks key-order differences. HMAC would require distributing a shared secret to apps.

Exact promotion

Decision
The manifest contains no channel. Staging and Production pointers reference immutable signed releases; promotion reuses the Staging manifest digest and payload and creates only a Production channel event.
Rationale
This proves that Production is the verified Staging candidate rather than a rebuild.
Alternatives
Embedding the channel in the manifest would force a byte change during promotion.

Media

Decision
Store bounded image bytes in D1 chunks and store external HTTPS metadata for audio/video. Public media is authorized by reachability from the active Production manifest.
Rationale
Images need same-origin durability; large streaming media does not belong in D1. Reachability prevents draft leakage.
Alternatives
Public-by-ID media leaks abandoned drafts. Large binary D1 storage is inefficient.

Application shape

Single TypeScript package

Decision
Retain React, Vite, TypeScript, and the existing Worker entrypoint; add Hono for explicit routing and middleware plus layered domain/repository/service modules.
Rationale
This preserves the working foundation and keeps client/server contracts in one strict TypeScript project.
Alternatives
A monorepo or framework rewrite adds risk without improving this single-product deployment.

Notification scope

Decision
Author and sign notification campaigns as PointApp content. Do not claim native push delivery until the separate app and APNs/FCM provider exist.
Rationale
The Builder can own the content contract without pretending to own unavailable native infrastructure.
Alternatives
Embedding provider credentials now creates unused secret and operational surface.

Quality gates

Decision
Require format, generated bindings, strict types, lint, OpenAPI lint, migration rehearsal, unit/integration coverage, dependency audit, production build, performance checks, Playwright responsiveness/accessibility, and live verification.
Rationale
Authentication and exact release promotion are high-impact; each invariant needs executable evidence.
Alternatives
A single happy-path browser test cannot validate server-side access or immutable promotion.
