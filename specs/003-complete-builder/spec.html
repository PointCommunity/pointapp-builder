Specification 003 · Complete production product

A real control plane for the PointApp.

PointApp Builder is the private, role-governed authoring and release system for the public content rendered by installed PointApp phone and tablet clients. This specification replaces the disconnected foundation behavior with working authentication, persistence, editing, Staging, Production, audit, and delivery capabilities.

Two meanings of Production: PointApp Builder has one deployment environment, Production at appbuilder.pointatx.org. Inside that Builder, PointApp content moves from Draft to the PointApp Staging channel and then to the PointApp Production channel. The channels are content states, not deployments of the Builder application.

1. Prioritized user journeys

P1

Bootstrap ownership and govern access

The designated bootstrap GitHub identity signs in for the first time and becomes the initial Owner. Every later first-time user is recorded as a pending Editor. Owners review, approve, disable, and assign roles; Administrators may manage only Editors and Publishers.

Independent test: start with an empty database, complete three identity logins, and prove bootstrap, pending, approval, role bounds, last-Owner protection, and audit records.

P1

Author and preserve app content

An Editor creates a draft, manages screens and elements, configures navigation and brand settings, sees the same manifest in phone and tablet previews, and saves immutable revisions without losing concurrent work.

Independent test: create, edit, save, reload, duplicate, archive, and recover a draft while proving optimistic-conflict behavior.

P1

Release exact content to devices

A Publisher publishes an exact revision to PointApp Staging. An Administrator or Owner promotes that unchanged verified envelope to PointApp Production. Installed apps can fetch, verify, cache, and atomically activate the new manifest without an app-store release.

Independent test: publish and promote, then compare revision, digest, envelope, ETag, signature, history, and rollback behavior byte-for-byte.

P2

Operate every Builder panel

Content, Library, Navigation, Branding, Audience, Notifications, Releases, Access, and Settings each expose useful persisted behavior appropriate to the actor’s role.

Independent test: complete the primary flow in each panel and reload the workspace to prove persistence.

P2

Audit and recover safely

Owners can inspect access, content, release, and rollback activity. Production retains a last-known-good envelope and may roll back only to an existing signed Production release.

Independent test: create several releases, roll back to one, and prove the channel pointer and audit history while preserving every immutable release.

P3

Work comfortably on common screens

The authenticated Builder remains keyboard-accessible and usable on mobile, tablet, and desktop screens, while its preview explicitly models installed phone and tablet layouts.

Independent test: run the full author/publish/admin paths at representative viewport sizes with no inaccessible controls or horizontal page clipping.

2. Acceptance scenarios

  1. Given no memberships exist, when GitHub user ID 1202831 signs in, then one active Owner membership is created and audited.
  2. Given an Owner already exists, when any new valid GitHub identity signs in, then a pending Editor request is created and protected content remains unavailable.
  3. Given a pending user, when an Owner approves the request, then that user can enter as an Editor on the next authenticated request.
  4. Given an Editor’s current revision, when the Editor changes an element and saves, then a new immutable revision is stored and the prior revision remains retrievable.
  5. Given two editors started from the same revision, when one has already saved, then the other receives a conflict and no work is silently overwritten.
  6. Given a valid draft revision, when a Publisher publishes to Staging, then a signed immutable Staging envelope is stored and rendered in the Staging preview.
  7. Given an exact Staging envelope, when an Administrator or Owner promotes it, then Production points to the identical manifest digest without rebuilding it.
  8. Given a device requests Production with the current ETag, when no release changed, then it receives 304; after promotion it receives the new signed envelope immediately.
  9. Given a prior Production release, when an Owner rolls back, then the channel advances to that already-signed release and records the rollback actor and reason.
  10. Given an unauthorized or pending actor, when any protected mutation is attempted, then the API denies it even if a request is constructed outside the UI.

3. Functional requirements

Authentication and access

  • FR-001: Authenticate users through the existing organization-owned pointsite-builder GitHub App using exact callback URLs, state, PKCE, short-lived authorization codes, and signed Secure HttpOnly sessions.
  • FR-002: Configure that existing GitHub App installation for all PointCommunity repositories without expanding its current repository permissions.
  • FR-003: Permit only fixed GitHub user ID 1202831 to bootstrap an empty installation as the first Owner.
  • FR-004: Register every other first-time authenticated identity as role Editor with status Pending; never grant content access before approval.
  • FR-005: Preserve the ordered roles Editor, Publisher, Administrator, and Owner and enforce every capability server-side.
  • FR-006: Allow Owners to approve, disable, reactivate, and assign any role; allow Administrators to manage only Editors and Publishers.
  • FR-007: Prevent disabling or demoting the last active Owner and prevent self-lockout when it would leave no Owner.
  • FR-008: Re-read membership status and role on every protected request so revocation takes effect immediately.
  • FR-009: Remove the simulated role selector and show the authenticated identity, actual role/status, and sign-out action.
  • FR-010: Present distinct signed-out, pending, disabled, unavailable, and authenticated states without leaking protected data.

Content, media, and configuration

  • FR-011: Support multiple named drafts with create, duplicate, archive, recover, and non-destructive history behavior.
  • FR-012: Store each save as a new immutable revision with parent, sequence, checksum, actor, label, schema version, and timestamp.
  • FR-013: Reject a save whose expected parent is stale and return enough safe information to reload without overwriting newer work.
  • FR-014: Let Editors create, rename, duplicate, reorder, hide, and delete screens while preserving valid navigation targets.
  • FR-015: Let Editors add, edit, duplicate, move, reorder, and remove supported elements: Hero, Rich Text, Action, Image, Video, Audio, Card List, Event List, Scripture, Divider, Spacer, and Embed Link.
  • FR-016: Validate all text, links, identifiers, counts, media references, dates, audience rules, and presentation values against bounded allowlists.
  • FR-017: Let Editors upload JPEG, PNG, WebP, and AVIF images and bounded audio/video metadata; reject unsupported type, size, dimensions, checksum, or missing accessibility metadata.
  • FR-018: Serve private draft media only to active members and public media only when referenced by the active Production release.
  • FR-019: Let Editors configure two-to-five bottom navigation items targeting existing visible screens with supported icons.
  • FR-020: Let Editors configure app identity, approved color tokens, logo media, typography scale, corner style, and light/dark presentation tokens.
  • FR-021: Let Editors define audience segments and apply explicit segment visibility to screens and elements without storing member personal data.
  • FR-022: Let Editors create notification campaigns with title, body, destination, audience, status, and optional scheduled time; campaigns are delivered as signed PointApp content, not sent through an unconfigured native push provider.
  • FR-023: Let authorized users configure organization identity, support links, default locale/time zone, refresh guidance, and minimum compatible manifest schema.
  • FR-024: Render the same manifest semantics in switchable phone and tablet previews, including screen navigation and audience selection.
  • FR-025: Persist useful changes from every Builder panel; no panel may remain a placeholder or simulated success path.

Staging, Production, and installed-app delivery

  • FR-026: Allow Publishers, Administrators, and Owners to publish one exact saved revision to the PointApp Staging channel.
  • FR-027: Validate schema, navigation, media readiness, accessibility fields, link policy, compatibility, and notification timing before Staging publication.
  • FR-028: Create a canonical immutable release envelope containing manifest revision, digest, release time, channel, signing algorithm, signature, and key identifier.
  • FR-029: Allow only Administrators and Owners to promote the current verified Staging release to Production.
  • FR-030: Promote without rebuilding or altering the Staging manifest payload; the manifest digest must remain identical.
  • FR-031: Expose a public, read-only, versioned Production channel endpoint supporting HTTPS, ETag conditional requests, explicit cache behavior, and safe compatibility metadata.
  • FR-032: Expose the signing public key and retain the private signing key only as a Worker secret.
  • FR-033: Preserve immutable release history and a last-known-good Production pointer.
  • FR-034: Allow Owners to roll back only to a previously signed Production release and require a bounded reason.
  • FR-035: Return a changed ETag immediately after Production promotion or rollback so online apps can fetch and atomically activate the new content; offline delivery occurs at the next refresh.

Security, operations, and Builder delivery

  • FR-036: Require exact same-origin mutation requests, allowed content types, bounded bodies, idempotency keys for retryable mutations, and per-actor/IP rate limits.
  • FR-037: Apply restrictive security headers and never expose credentials, stack traces, raw database errors, private records, or signing material.
  • FR-038: Record successful, denied, and failed access, draft, media, release, rollback, and settings mutations with request correlation IDs.
  • FR-039: Provide Owner-visible audit history, release history, resource capacity, and system health without exposing secret values.
  • FR-040: Use backward-compatible, locally rehearsed D1 migrations and refuse application startup when configuration is incomplete outside local development.
  • FR-041: Provide deterministic local identity fixtures that cannot activate on non-loopback or Production requests.
  • FR-042: Keep the private source repository and the public Worker shell separated; unauthenticated requests may access only login, health, public Production content, its referenced public media, and static assets.
  • FR-043: Meet the WCAG 2.2 AA target for semantics, labels, focus, contrast, keyboard operation, status announcements, reduced motion, and 44-pixel touch targets.
  • FR-044: Keep primary API reads below 250 ms p95 and authenticated saves below 500 ms p95 in the repository load profile, excluding GitHub OAuth latency.
  • FR-045: Run formatting, generated-type, type, lint, contract, migration, unit/integration coverage, build, dependency audit, performance, responsive browser, accessibility, and live verification gates.
  • FR-046: Develop, build, and deploy PointApp Builder directly to its single Production environment only after the exact commit passes all gates; never create a Builder canary/staging environment.

4. Key entities

Entity Purpose and invariant
GitHub identity Stable GitHub numeric ID and normalized login; identity is not authority by itself.
Membership Role plus Pending, Active, or Disabled status; every protected request consults current state.
Draft Named mutable workspace whose saves point to immutable revisions.
Revision Canonical PointApp manifest snapshot with parent, sequence, checksum, schema, actor, and time.
Manifest Data-only app identity, settings, theme, audiences, navigation, screens, elements, media references, and notification campaigns.
Media asset Validated private object and metadata; becomes public only through active Production reference.
Release envelope Immutable signed revision for Staging or Production with digest and compatibility metadata.
Channel pointer Atomic Staging or Production reference to one immutable release.
Audit event Append-only actor, action, target, outcome, request ID, time, and bounded safe metadata.
Idempotency record Actor-scoped replay protection for retryable mutations.

5. Edge cases and required outcomes

  • An arbitrary user reaches the empty installation before the designated Owner: they become Pending, never Owner.
  • The bootstrap identity signs in after pending requests exist but no Owner exists: the bootstrap identity becomes Owner atomically.
  • Two bootstrap requests race: database uniqueness yields exactly one active Owner record.
  • A login changes capitalization or username: stable GitHub ID retains membership and updates the display login.
  • An Owner attempts to remove the last Owner: reject without state change.
  • A user is disabled mid-session: the next protected request is denied.
  • A screen targeted by navigation is hidden/deleted: reject or repair only through an explicit user choice.
  • An element references unavailable media: reject Staging publication and identify the element safely.
  • A scheduled notification time is in the past: require explicit immediate-send confirmation represented as an immediate campaign state.
  • A Production promotion retries after a network failure: the same idempotency key returns the original result.
  • Signing configuration is missing: editing remains available, but all releases fail closed with an operator-safe message.
  • A public client sends a malformed ETag or unsupported schema: return a safe bounded response without exposing draft state.

6. Measurable success criteria

  • SC-001: In an empty local installation, the designated identity reaches an active Owner workspace in one login; three later identities are all pending Editors with zero protected-data responses.
  • SC-002: Every one of the nine named panels completes at least one persisted end-to-end user flow and reloads the saved result.
  • SC-003: A complete create-edit-save-Staging-Production journey succeeds without manual database or repository intervention.
  • SC-004: Staging and promoted Production manifest digests are identical in 100% of release tests.
  • SC-005: Unauthorized role/capability combinations are denied in 100% of the executable access matrix.
  • SC-006: All automated tests pass with no unexplained skips and every configured coverage threshold passes.
  • SC-007: Phone, tablet portrait, tablet landscape, and desktop tests show no page-level horizontal clipping, keyboard traps, or automatically detectable accessibility violations.
  • SC-008: Primary read requests meet 250 ms p95 and saves meet 500 ms p95 under the repository’s repeatable load profile.
  • SC-009: The exact reviewed main commit passes GitHub Quality, deploys to appbuilder.pointatx.org, and passes live HTTPS, health, content-channel, asset, and browser checks.
  • SC-010: The final handoff states all remaining external/native dependencies plainly and invites the Owner to begin human testing only after every automated and agent-operated gate is green.

7. Explicit boundaries

Included

Builder authentication, access governance, authoring, media, revision persistence, Staging/Production content channels, signatures, public delivery, rollback, audit, direct Builder Production deployment, and GitHub App organization configuration.

Separate

Native PointApp implementation, Apple/Google submissions, device push-provider credentials, and app-side polling/verification/cache code. This Builder delivers the contract those clients consume.

Never

Browser-selected authority, arbitrary first-user ownership, executable downloaded content, Production rebuilt from a different candidate, public drafts/media, secret-bearing source, destructive migration recovery, or a second Builder environment.
