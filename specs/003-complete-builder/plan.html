Implementation plan · codex/003-complete-builder

From prototype to production control plane.

A single Cloudflare Worker serves the authenticated Builder and the signed public PointApp content channel. The plan advances in independently verifiable vertical slices, with access and release invariants established before broad UI work.

Technical baseline

Runtime

Node.js 22+, TypeScript 5.9 strict mode, React 19, Vite 8, Hono, Zod, Cloudflare Worker Static Assets.

Persistence

Cloudflare D1 with forward-only migrations, immutable revisions, transactional pointer changes, idempotency records, audit events, and chunked images.

Verification

Vitest/Miniflare, Testing Library, Redocly, Playwright, axe-core, deterministic load checks, dependency audit, production build, CI, and live checks.

Execution sequence

01

Secure foundation

Add D1 migrations, Hono composition, typed errors, correlation IDs, security headers, request bounds, CSRF/origin enforcement, idempotency, and rate limiting. Contract and migration tests lead implementation.

02

Identity and governance

Implement GitHub App OAuth with state and PKCE, signed __Host- cookies, fixed Owner bootstrap, Pending Editor registration, immediate role/status lookup, full access matrix, last-Owner protection, and audit logging.

03

Authoring core

Implement draft/revision repositories with optimistic concurrency, schema validation, duplicate/archive/recover operations, and API client state. Build screen, element, navigation, branding, audience, notification, and settings editors against the same manifest.

04

Media and preview

Add bounded accessible image upload, external audio/video metadata, private/public reachability rules, phone/tablet responsive previews, navigation interaction, and audience simulation.

05

Immutable release system

Canonicalize and hash manifests; validate releases; sign with Ed25519; publish exact saved revisions to PointApp Staging; promote the same digest to Production; expose ETag-aware public content/key/media routes; add history and reasoned rollback.

06

Operations and complete UI

Replace every placeholder and simulated control. Deliver real Access, Releases, Audit/health/capacity, Content, Library, Navigation, Branding, Audience, Notifications, and Settings panels with accessible loading/error/empty states.

07

Adversarial verification

Execute the role matrix, stale-write tests, malformed media/manifest tests, replay/idempotency tests, signature/digest invariants, route privacy checks, performance load profile, responsive browser matrix, keyboard and automated accessibility checks.

08

Organization integration and production

Add the exact PointApp callback to the existing GitHub App, expand only its repository selection to all organization repositories, install Builder-specific secrets, migrate D1, merge the reviewed branch, require green CI for the exact main commit, deploy directly to Builder Production, and verify live.

Architecture boundaries

Client

No authority or durable truth. It renders current server capabilities and submits expected revision IDs.

Worker API

Owns authentication, authorization, validation, orchestration, signatures, public delivery, and audit correlation.

D1

Owns membership state, immutable content/release records, mutable channel pointers, idempotency, and audit evidence.

PointApp

Separate native consumer. It will verify signatures and atomically activate compatible data; it is not modified here.

Governance gates

All constitution gates pass.

  • Server authority and stable bootstrap identity are mandatory before protected features.
  • No promotion path may alter the verified Staging manifest digest.
  • No Builder pre-production environment will be created.
  • No remote deployment occurs from an uncommitted or failing tree.
  • Human testing begins only after automated and agent-operated gates are fully green.

Explicit dependency on the Owner

The registration-boundary assumption remains open for confirmation: all valid GitHub users may request access as Pending Editors. It does not block safe implementation because Pending users receive no protected data. Final human validation will also require the Owner to exercise real editorial judgment on representative phone/tablet content.
