Specification 001 · Foundation

PointApp Builder

A private, role-governed authoring system for content that the PointApp can receive as signed, versioned data updates on phones and tablets.

Scope boundary: this foundation establishes the product contract, repository, access policy, responsive Builder shell, phone/tablet staging preview, content manifest, tests, and deployment path. It does not claim to deliver the complete Builder, authentication service, native PointApp, app-store releases, or a production content channel.

1. Objective

Authors

Editors arrange app content and elements without editing application source.

Release staff

Publishers prove an exact content candidate in Staging; Administrators and Owners may later promote the verified candidate.

App users

Installed phone and tablet apps receive approved content without downloading executable code or waiting for a store release.

2. Architecture contract

  1. The Builder edits a typed content manifest, never native executable code.
  2. Every save creates a revision; every release identifies one immutable revision and digest.
  3. Staging and Production are separate release channels backed by the same renderer contract.
  4. The web staging preview uses the same manifest semantics and device breakpoints as PointApp.
  5. The installed app polls or receives a push hint, downloads the signed manifest, verifies schema/version/digest/signature, stores it atomically, and retains the last-known-good manifest for rollback.
  6. Native capabilities and executable changes continue through Apple App Store and Google Play releases.

3. Access policy

Capability Editor Publisher Administrator Owner
Edit drafts and assets Yes Yes Yes
Publish exact revision to Staging No Yes Yes
Promote verified Staging revision No No Yes Yes
Manage Editors and Publishers No No Yes Yes
Manage Administrators / ownership No No No Yes

Authorization must be enforced by the future API. Hidden or disabled browser controls are guidance only, never the security boundary.

4. Initial content model

A manifest contains organization identity, theme tokens, bottom navigation, ordered screens, reusable assets, content elements, schema version, release revision, and timestamps. Foundation elements are hero, text, action, media, event-list, and divider. New element types require schema, renderer, inspector, accessibility, migration, and compatibility tests.

5. Technology and hosting

  • React, strict TypeScript, Vite, Zod, Vitest, Testing Library, and Playwright.
  • GitHub Pages serves only the static Builder client. No secret, role assignment, draft, or release credential may be bundled into it.
  • A separate authenticated API and durable store will be selected before collaborative editing begins.
  • The current PointCommunity GitHub Free plan cannot publish Pages from this private organization repository. The Pages workflow remains manually gated until the plan or host decision changes.

8. Code style

export function can(actor: Actor, capability: Capability): boolean {
  return roleCapabilities[actor.role].includes(capability);
}

Use explicit domain names, pure functions for policy, discriminated unions for elements, exhaustive rendering, semantic HTML, and mobile-first CSS. Keep platform concerns behind interfaces.

9. Testing strategy

  • Unit tests prove access inheritance, manifest validation, element compatibility, and release transitions.
  • Component tests prove controls reflect policy and previews render the manifest.
  • Browser tests cover keyboard access and 320, 768, 1024, and 1280 pixel layouts with no horizontal clipping.
  • Contract fixtures must be consumable independently by future iOS and Android clients.

10. Boundaries

Always

Validate inputs, identify exact revisions, preserve last-known-good content, test permissions server-side, keep staging distinct, and maintain accessible touch targets.

Ask first

Select the backend/identity provider, enable public exposure, create production credentials, connect PointApp, promote Production, or begin store submissions.

Never

Place secrets in Pages, treat client-side roles as security, directly mutate PointApp source, ship executable code in content manifests, silently overwrite a newer revision, or bypass app-store release controls.

11. Foundation success criteria

  • A private PointCommunity/pointapp-builder repository exists with an auditable initial commit.
  • The responsive shell exposes separated Content, Library, Navigation, Branding, Audience, Notifications, Releases, Access, and Settings panels.
  • A representative manifest renders in both phone and tablet staging frames.
  • The four-role capability matrix and versioned manifest are executable, tested contracts.
  • Quality, build, and browser checks pass locally and in GitHub Actions.
  • Pages deployment is configured but cannot activate from a private repository until the organization plan supports it.

12. Deferred decisions

  • Identity provider and account recovery.
  • Authenticated API/store host and operating-cost ceiling.
  • Production approval details beyond the initial Administrator/Owner gate.
  • Native PointApp framework, offline media policy, push provider, analytics, and app-store accounts.
  • Whether PointApp remains Point-only or later becomes multi-organization.
