Specification 002 · Hosting

Cloudflare hosting,
isolated by product.

PointApp Builder will use the same hosting shape as PointSite Builder while retaining its own Worker, domain, data store, configuration, and future authentication credentials.

Approved domain: appbuilder.pointatx.org. The initial deployment may expose only the disconnected foundation interface and health endpoint. Authentication, drafts, and publishing remain unavailable until separately implemented and configured.

Objective

Deploy the exact reviewed PointApp Builder source as a Cloudflare Worker that serves the Vite application, routes API and authentication requests through Worker code, verifies access to the Point Community Cloudflare account before deployment, and binds a dedicated D1 database.

Resources

Worker

pointapp-builder, with observability enabled and public preview URLs disabled.

Domain

appbuilder.pointatx.org as a Worker custom domain.

Database

A dedicated D1 database named pointapp-builder. It must never reuse PointSite Builder data.

Assets

The Vite build is served by the Worker assets binding with single-page application fallback.

Runtime behavior

  • GET /api/health returns environment, app version, and D1 reachability.
  • Unknown /api/* and /auth/* routes fail closed with a JSON 503 FOUNDATION_LOCKED response.
  • All remaining requests resolve through the compiled static application.
  • The deployed client continues to label itself as disconnected foundation mode; no client-selected role is an authorization decision.

Code style

if (url.pathname === '/api/health') {
  return healthResponse(await checkDatabase(env.DB));
}
return lockedResponse();

Keep routing explicit, responses deterministic, public metadata minimal, errors fail-closed, and environment configuration validated before use.

Testing strategy

  • Unit tests prove the health contract, D1 failure behavior, and locked unknown API/auth routes.
  • The existing full quality and browser suites must remain green.
  • Before release, build from a clean exact commit and record the previous Worker deployment.
  • After release, verify Cloudflare deployment identity, TLS, health, HTML-derived assets, responsive UI, and browser console state.

Boundaries

Always

Use the verified Point Community Cloudflare account, isolated resources, exact committed source, and post-deploy live evidence.

Ask first

Add authentication credentials, enable draft mutations, connect PointApp delivery, or enable Production publishing.

Never

Reuse PointSite D1 data or auth secrets, expose credentials, deploy a dirty tree, or represent foundation controls as real authorization.

Success criteria

  • The dedicated D1 resource and Worker deployment exist in the expected Cloudflare account.
  • https://appbuilder.pointatx.org serves the PointApp Builder foundation over HTTPS.
  • The live health endpoint reports the deployed version and reachable database.
  • Unknown API and authentication routes fail closed.
  • Local and GitHub quality gates pass on the exact deployed commit.
  • The obsolete GitHub Pages workflow is removed and human-facing hosting documentation describes Cloudflare.
