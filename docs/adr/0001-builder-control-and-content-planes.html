Architecture decision record · 0001

Accepted

Separate the private Builder control plane from the signed PointApp content plane.

Date: 7 September 2026 · Owners: Point Community Church / PointApp Builder

Context

The PointApp Builder is an authenticated authoring and release-control application. Installed PointApps need immediate content updates without requiring an App Store or Play Store release for every editorial change. Executable native functionality must still ship through the stores. The Builder itself has one Production deployment; “Staging” and “Production” inside it refer only to PointApp content channels.

Decision

  • Host the React Builder and Worker API together at appbuilder.pointatx.org.
  • Store identities, memberships, drafts, immutable revisions, media metadata/approved image bytes, release history, channel pointers, idempotency, and audit evidence in D1.
  • Authenticate with the existing organization GitHub App, but authorize every request from current D1 membership.
  • Publish canonical, immutable, Ed25519-signed data manifests. PointApp Staging accepts Publisher+; Production accepts only exact current Staging candidates from Administrator+.
  • Expose anonymous, read-only, versioned Production content, public key, and referenced media endpoints with ETags and explicit cache semantics.
  • Keep the native PointApp and app-store workflow outside this repository.

Consequences

Positive

  • Editorial updates can reach online installed apps as content without native release delay.
  • The public client does not need Builder credentials and can cryptographically verify provenance.
  • Production promotion has a provable same-digest relationship to Staging.
  • One Worker deployment reduces operational coupling while route-level trust boundaries remain explicit.

Costs and obligations

  • The native app must implement signature verification, schema compatibility, atomic activation, refresh/backoff, and last-known-good caching.
  • D1 migrations and channel-pointer transactions become release-critical.
  • Key identifiers and rotation must be supported before replacing the signing key.
  • “Immediate” means available on next online refresh; offline devices cannot be forced to update.

Rejected alternatives

  • Commit every content change to GitHub: broader permissions, slower publication, and difficult optimistic collaboration.
  • Put roles/drafts in the SPA: publicly inspectable and unenforceable.
  • Rebuild for Production: breaks exact-candidate proof.
  • Deliver JavaScript/configured executable behavior: crosses the data-only boundary and app-store governance.
  • Create a Builder staging deployment: contradicts the established one-Production operating model.

Revisit when

A second organization/tenant is added, media scale requires R2, a native push provider is selected, registration becomes organization-members-only, or signing-key rotation requirements change.
